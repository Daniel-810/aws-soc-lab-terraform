# ADR-036. 배포 검증을 스크립트 하나로 묶고, EC2 역할에 출처 계정 조건을 둔다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 일자 | 2026-09-26 |
| 관련 | `NFR-03`, `AC-03`, `AC-08`, `SR-06`, `ADR-020`, `ADR-024`, `docs/04-audit-prowler.md`, `docs/05-verification.md` |

---

## 맥락

Phase 11 판정에서 두 인수 기준이 부분 충족으로 남았다.

- `AC-03`: 재생성 후 검증이 사람 손에 달려 있었다. 탐지 측정만 도구로 자동화돼 있었고, 노출, 인스턴스 설정, 세션 관리자, 헤더 위조, 시간 동기화, 로그 도착 같은 점검은 명령을 하나씩 쳐서 확인했다.
- `AC-08`: 자체 감사가 세 EC2 역할의 신뢰 정책에 출처 조건이 없다고 지적했다(혼동된 대리인). EC2가 인스턴스 자격증명을 줄 때 이 조건 키를 넣는지 확인하지 못해 판단을 보류했다. 잘못 넣으면 인스턴스가 자격증명을 받지 못해 관리 접근이 끊긴다.

## 결정

- **배포 검증 스크립트(`tools/verify`)를 둔다.** 검증에서 손으로 한 점검 12가지를 명령 하나로 실행하고, 하나라도 실패하면 0이 아닌 종료 코드를 돌려준다. 측정 도구의 요청과 원격 실행 함수를 재사용한다.
- **세 EC2 역할의 신뢰 정책에 `aws:SourceAccount` 조건을 둔다.**

## 근거

- **검증이 사람에게 달려 있으면 재생성할 때마다 빠지는 점검이 생긴다.** 스크립트는 같은 기준을 매번 같은 순서로 적용한다.
- **조건은 배포로 확인한 뒤 넣었다.** 조건을 넣은 채로 배포했을 때 세 인스턴스 모두 세션 관리자에 연결됐고, 웹 방화벽은 역할 권한으로 시크릿을 읽어 기동했으며, 로그 에이전트도 로그를 보냈다. EC2가 역할을 맡을 때 이 키를 넣는다는 뜻이다. 재감사에서 세 역할 모두 통과로 바뀌었다.
- 조건은 다른 계정의 요청으로 이 역할이 쓰이는 경로를 막는다. 동작을 바꾸지 않고 막을 수 있는 것은 막는다.

## 고려한 대안

**점검 목록 문서만 두기** — 만들기 쉽다. 사람이 실행해야 하는 것은 그대로다.

**CI에서 배포까지 해서 검증** — 가장 자동화된다. 공개 저장소의 CI가 계정에 접근해야 하고 비용이 든다(`ADR-033`).

**역할 조건을 수용 항목으로 기록** — 배포가 필요 없다. 확인할 수 있는 것을 확인하지 않은 채 남긴다.

## 결과

- 스크립트를 처음 돌렸을 때 세 점검이 실패했고, 모두 스크립트나 절차의 문제였다.
  - **경로를 켠 직후에는 평문 공격이 아직 IPS를 거치지 않았다.** 게이트웨이 엣지 경로가 반영되기까지 수십 초가 걸려, 그동안 공격이 웹 방화벽으로 바로 갔다. 이 점검은 경로를 켠 상태면 최대 90초 동안 재시도한다. 이전 수동 시험은 전환 후 1분쯤 지나 보냈기 때문에 드러나지 않았다.
  - 앱 이미지가 distroless라 컨테이너에 셸이 없고 node가 전체 경로에만 있다.
  - 로그 도착 점검이 공격을 보내기 전에 돌면 IPS 경보가 아직 없다. 맨 마지막으로 옮겼다.
- **탐지율은 HTTPS 경로에서 잰다.** 경로를 켜면 평문 공격 일부를 IPS가 먼저 떨어뜨려 웹 방화벽에 닿지 않는다. 두 경로를 합쳐 세면 웹 방화벽 탐지율이 42.9%로 낮게 나왔고, HTTPS에서 재면 이전 측정과 같은 44.7%다. 실제 트래픽 오탐은 모든 계층, 두 경로를 합쳐 0건이어야 한다.
- 메타데이터 차단 점검에는 대조군을 둔다. 같은 인스턴스의 호스트는 응답을 받아야 하고, 컨테이너는 받지 못해야 한다. 컨테이너만 보면 다른 이유로 실패해도 차단으로 읽힌다.
- 스크립트는 배포된 랩이 있어야 돈다. 실행 시간은 탐지 측정을 포함해 약 100초다.
