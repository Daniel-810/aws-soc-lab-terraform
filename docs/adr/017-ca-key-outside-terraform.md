# ADR-017. 인증 기관의 개인 키를 Terraform이 다루지 않는다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 일자 | 2026-09-08 |
| 관련 | `SR-24`, `SR-08`, `SR-09`, `SR-06`, `SR-07`, `ADR-011`, `T-21`, `F3` |

---

## 맥락

`ADR-011`은 내부 구간 TLS에 코드로 생성한 사설 인증 기관을 쓰기로 정했다. 그 문서의 결과 항목에는 "인증 기관의 개인 키가 상태 파일에 포함될 수 있다"고 적혀 있고, 대응으로 `SR-09`(저장 시 암호화)와 `SR-24`를 적용하라고만 되어 있었다.

이번 Phase에서 실제로 구현하려고 보니 그 대응이 성립하지 않는다. `SR-24`는 시크릿이 **상태 파일에 평문으로 포함되지 않을 것**을 요구하는데, Terraform 상태 파일에는 리소스의 모든 속성이 평문으로 기록되며 예외가 없다. 저장소를 암호화해도 이는 `SR-09`를 충족할 뿐 `SR-24`를 면제하지 않는다. 두 요구사항은 대상이 다르다.

문제는 도구를 무엇으로 쓰느냐가 아니라 **Terraform이 값을 거치는가**이다.

- 인증서 리소스로 키를 생성하면 개인 키가 상태에 기록된다.
- 생성한 키를 시크릿 관리 서비스에 넣어도, 넣은 값이 그대로 상태에 기록된다.
- 나중에 데이터 소스로 읽어도, 읽어 온 값이 상태에 기록된다.

즉 시크릿 관리 서비스를 도입했다는 사실만으로는 아무것도 해결되지 않는다.

## 결정

**Terraform은 빈 시크릿과 그 접근 정책까지만 만든다.** 인증 기관 생성과 서버 인증서 서명은 애플리케이션 인스턴스가 부팅 시점에 수행하고, 개인 키는 해당 인스턴스 밖으로 나가지 않는다. 시크릿에 저장하는 것은 검증에만 필요한 **공개 인증서 한 건**이며, 웹 방화벽 인스턴스는 부팅 시 이를 읽어 신뢰 저장소에 추가한다.

```
Terraform
  빈 시크릿과 IAM 정책만 생성한다. 값을 쓰지 않는다.

애플리케이션 인스턴스 (부팅 시)
  인증 기관을 생성한다. 개인 키는 이 인스턴스 안에만 존재한다.
  자신의 서버 인증서를 그 기관으로 서명한다.
  공개 인증서만 시크릿에 저장한다.

웹 방화벽 인스턴스 (부팅 시)
  시크릿에서 공개 인증서를 읽어 신뢰 저장소에 추가한다.
  이후 애플리케이션으로 가는 연결에서 검증이 성공한다.
```

`ADR-011`의 "Terraform으로 사설 인증 기관을 생성한다"는 이 범위에서 개정된다. 사설 인증 기관을 쓰기로 한 결정 자체는 유지된다.

## 근거

- 개인 키가 상태 파일에도, 시크릿 저장소에도, 코드에도 존재하지 않으므로 `SR-24`가 회피가 아니라 구조로 충족된다.
- 공유되는 것은 공개 인증서뿐이고, 공개 인증서는 원래 공개를 전제로 만들어진 물건이다. 유출을 걱정할 대상이 아니다.
- 검증에 필요한 것은 서명한 기관을 신뢰할 근거이지 개인 키가 아니다. 요구사항이 필요로 하는 최소치만 전달하는 구성이다.
- 상태 파일이 평문이라는 사실은 도구의 성질이므로, 통제는 저장소 보호가 아니라 **무엇을 상태에 넣지 않을 것인가**로 설계해야 한다.

## 고려한 대안

**인증서 리소스로 키를 만들고 상태 저장소 암호화에 의존** — 가장 흔한 구성이고 코드가 짧다. `SR-09`는 충족하지만 `SR-24`를 정면으로 위반한다. 상태 파일을 읽을 수 있는 사람은 곧 인증 기관을 소유하게 된다.

**Terraform이 키를 만들어 시크릿 관리 서비스에 주입** — 키의 최종 보관 위치는 개선되지만 주입 과정에서 상태에 남으므로 문제가 해결되지 않는다. **시크릿 관리 서비스를 쓰면 안전하다는 오해가 정확히 이 지점에서 생긴다.**

**관리형 사설 인증 기관** — 개인 키가 서비스 밖으로 나오지 않아 구조적으로 가장 낫다. 월 고정비가 예산(`C-04`)을 초과한다. `ADR-011`에서 이미 배제했다.

**사전 제작 이미지에 키를 포함** — 상태 파일 문제는 사라지지만 키가 이미지에 남아 그 이미지를 읽을 수 있는 모든 주체에게 노출된다. 배포판 패키지 설치 원칙(`ADR-006`)과도 어긋난다.

## 결과

- **부팅 순서가 보장되지 않는다.** 두 인스턴스가 동시에 뜨므로 웹 방화벽이 시크릿을 읽으려 할 때 값이 아직 없을 수 있다. 초기화 스크립트에 재시도 루프와 타임아웃을 넣고, 초과 시 명확한 메시지와 함께 실패시킨다. **Terraform의 의존성 선언으로는 해결되지 않는다.** 인스턴스 생성 순서는 제어할 수 있어도 부팅 스크립트의 완료 순서는 제어할 수 없기 때문이다.
- **애플리케이션 인스턴스가 교체되면 인증 기관도 새로 생성된다.** 웹 방화벽이 이전 기관을 신뢰하고 있으면 검증이 실패한다. 두 인스턴스를 함께 교체해야 하며, 한쪽만 교체하는 변경은 `NFR-03`의 재생성 검증에서 걸러져야 한다. **이것이 이 구조가 치르는 가장 큰 비용이다.**
- **시크릿의 복구 대기 기간을 0으로 설정한다.** 이 환경은 매번 삭제하고 다시 만드는 방식으로 운영하는데, 삭제 대기 중인 같은 이름의 시크릿이 남아 있으면 재생성이 이름 충돌로 실패한다. 프로덕션에서는 실수로 지운 시크릿을 되살릴 수 없게 되므로 절대 이렇게 설정하지 않는다. 랩의 운영 방식 때문에 허용하는 값이며 코드에 그 사실을 주석으로 남긴다.
- **역할을 읽기와 쓰기로 나눈다.** 애플리케이션 역할은 쓰기, 웹 방화벽 역할은 읽기만 가지며 대상은 해당 시크릿으로 한정한다(`SR-06`). 두 역할을 공유하지 않는다(`SR-07`).
- 개인 키를 사람도 확인할 수 없다. 인증서 문제를 디버깅할 때는 세션으로 인스턴스에 접속해 그 안에서 확인해야 한다.

### 배포 후 확인 (2026-09-25)

- **시크릿에 남은 이전 값이 경쟁 상태를 만들었다.** 한 번의 적용에서 앱과 웹 방화벽이 함께 교체되자, 웹 방화벽이 먼저 부팅해 이전 앱이 게시한 인증 기관 인증서를 읽었고 새 앱의 인증서 검증에 실패했다. 처음부터 배포할 때는 시크릿이 비어 있어 웹 방화벽이 새 값을 기다리므로 드러나지 않았다.
- 웹 방화벽은 이제 받은 인증 기관으로 앱의 인증서를 실제로 검증해 본 뒤에야 그 값을 신뢰하고, 실패하면 다시 받아 온다(최대 600초). 수정 후 같은 조건(두 인스턴스 동시 교체)에서 정상 기동을 확인했다.
