# ADR-009. NAT을 검사 계층 이전에 배치해 검사 지점을 단일화한다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 일자 | 2026-09-02 |
| 관련 | `FR-10`, `NFR-04`, `SR-15` |

---

## 맥락

아웃바운드 트래픽도 검사해야 한다(`FR-10`). 그런데 검사 서브넷의 라우팅 테이블은 하나이고, **인바운드 응답과 아웃바운드가 모두 목적지 `0.0.0.0/0`**이라 서로 다른 다음 홉으로 보낼 수 없다.

또한 관리형 방화벽은 **가용영역당 엔드포인트를 하나만** 생성할 수 있어, 단일 가용영역에서 검사 지점을 두 개 두려면 방화벽 리소스를 두 개 만들어야 한다.

## 결정

**앱 → NAT → 검사 계층 → 인터넷 게이트웨이** 순서로 배치한다. 검사 지점은 하나만 둔다.

## 근거

- 인바운드 응답과 아웃바운드가 **모두 최종적으로 인터넷 게이트웨이를 향하므로** `0.0.0.0/0 → IGW` 한 줄로 처리된다. 라우팅 충돌이 해소된다.
- 방화벽 리소스가 하나면 정책도 한 벌만 관리한다.
- 비용이 절반이 되어 예산(`NFR-04`) 내 기동 가능 시간이 두 배가 된다.
- 직접 운영 방식에서도 인스턴스 인터페이스가 하나면 충분해져 **다중 인터페이스 정책 라우팅이 불필요**해진다. 서브넷도 7개에서 5개로 줄어든다.

## 고려한 대안

**검사 지점 분리 (인바운드용 · 아웃바운드용)** — AWS 권장 구성이며 **아웃바운드 검사 시 원본 출발지 IP가 보존**된다. 그러나 단일 가용영역에서는 방화벽 리소스 두 개가 필요해 정책을 이중 관리해야 하고, 비용이 두 배가 되어 기동 가능 시간이 절반으로 줄어든다.

**아웃바운드 검사 미적용** — 가장 단순하고 비용이 낮다. 그러나 침해 후 외부 통신(C2)·데이터 유출을 관측할 수단이 사라진다.

## 결과

- **방화벽 로그의 출발지 주소가 NAT 게이트웨이 주소로 통일된다.** 어느 인스턴스에서 발생한 아웃바운드인지 방화벽 로그만으로는 식별할 수 없다.
- **보완**: VPC 흐름 로그(`SR-15`)로 NAT 전후 흐름을 대조해 추적한다. 흐름 로그와 방화벽 로그의 상관 키를 설계 단계에서 정의한다.
- 예산 제약이 없다면 대안(검사 지점 분리)이 기술적으로 옳다. 조건이 달라지면 재검토한다.
