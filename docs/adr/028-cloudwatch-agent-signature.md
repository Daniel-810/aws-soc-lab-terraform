# ADR-028. 로그 에이전트는 공개키 지문을 고정해 서명을 검증한 뒤 설치한다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 일자 | 2026-09-25 |
| 관련 | `FR-05`, `SR-06`, `SR-14`, `SR-22`, `SR-25`, `ADR-006`, `ADR-016`, `ADR-021` |

---

## 맥락

웹 방화벽과 Suricata의 로그를 CloudWatch로 보내려면 두 인스턴스(Ubuntu)에 로그 에이전트가 필요하다. Ubuntu 저장소에는 CloudWatch 에이전트 패키지가 없다. AWS는 자체 저장소에 패키지와 서명 파일, 공개키를 두고, 공개키의 지문을 문서에 공개한다.

지금까지 설치 경로는 배포판 저장소였다(`ADR-006`). 저장소 밖에서 받는 파일은 무결성을 직접 검증해야 해서, `ADR-016`은 같은 이유로 규칙 집합 최신판을 채택하지 않았다. 이번에는 배포판에 대안이 없다.

## 결정

**AWS가 공개한 패키지를 받아, 문서에 공개된 공개키 지문을 코드에 고정하고, 그 키로 만든 서명인지 검증한 뒤 설치한다.** 검증에 실패하면 초기 구성을 중단한다. 설치 스크립트는 저장소 최상위 `scripts/`에 두고 루트가 두 모듈에 같은 내용을 넘긴다. 설치된 버전은 파일에 기록한다.

## 근거

- **키 파일이 아니라 지문을 신뢰한다.** 키와 패키지를 같은 곳에서 받으므로, 그곳이 오염되면 둘 다 바뀔 수 있다. 서명 검증만으로는 이 경우를 막지 못한다. 문서로 교차 확인한 지문을 기준으로 삼아야 받은 키가 맞는 키인지 판단할 수 있다.
- **검증 결과를 한 번에 판정한다.** 서명이 유효할 때만 출력되는 상태 줄에 서명한 키의 지문이 함께 나온다. 그 줄에 고정한 지문이 있는지로 「파일이 온전하다」와 「기대한 키가 서명했다」를 함께 확인한다.
- **권한을 늘리지 않는다.** 역할에는 전용 로그 그룹에 대한 쓰기 권한만 있다. 세션 관리자 최소권한 5개(Phase 6에서 실측)를 유지한다.
- **설치 과정이 한 곳에 있다.** 두 인스턴스가 같은 스크립트를 쓰므로 검증 절차가 어긋나지 않는다(룰 파일과 같은 방식, `ADR-026`).

## 고려한 대안

**AWS 배포 서비스(Distributor)로 설치** — 서명 검증을 AWS가 대신한다. 인스턴스 역할에 세션 관리자 최소권한 외의 권한을 더 줘야 하고, 설치가 부팅 스크립트 밖에서 비동기로 일어나 초기 구성의 성공 여부를 한 곳에서 판단할 수 없다.

**검증 없이 설치** — 가장 단순하다. `SR-25`(공급망 무결성)를 위반한다.

**Python으로 전송기 직접 작성** — 웹 방화벽에 이미 SDK가 있어 가능하다. 파일 회전, 재시작 후 이어 읽기, 묶음 전송과 재시도를 직접 구현해야 하고, 그 신뢰성은 검증된 에이전트보다 낮다.

**서드파티 수집기(Fluent Bit 등) 저장소 추가** — 서명된 저장소라 검증은 된다. 신뢰해야 할 공급자가 하나 늘어난다.

## 결과

- 다운로드 경로가 최신 판만 제공하므로 버전을 고정할 수 없다. 설치 버전을 기록한다(`ADR-021`).
- AWS가 서명 키를 교체하면 초기 구성이 실패한다. 조용히 다른 키를 받아들이는 것보다 안전하며, 교체 시 문서의 새 지문으로 코드를 갱신한다.
- 에이전트는 로그 파일을 읽기 위해 루트로 실행된다. 파일 소유자 그룹에 에이전트 계정을 넣는 방식으로 좁힐 수 있으나, 로그마다 소유자가 달라 이번에는 적용하지 않았다.
- 에이전트가 쓰기 권한 두 개만으로 동작하는지는 배포로 확인한다.
