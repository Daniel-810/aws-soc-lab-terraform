# ADR-031. 차단 건수를 로그에서 지표로 만들고, 대시보드는 숫자와 추이를 먼저 보인다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 일자 | 2026-09-25 |
| 관련 | `FR-06`, `FR-07`, `NFR-04`, `ADR-030` |

---

## 맥락

Phase 10 첫 대시보드는 Logs Insights 표 네 개였다. 무엇이 얼마나, 언제 막혔는지가 한눈에 보이지 않았다. 로그 쿼리는 조사에는 맞지만 경보를 걸 수 없고, 두 방식의 로그 형식 차이를 쿼리마다 다시 풀어야 한다.

## 결정

- **로그 지표 필터로 계층별 건수를 지표로 만든다.** 웹 방화벽 차단(`WafBlocked`), IPS 차단(`IpsBlocked`), 흐름 거부(`FlowRejected`). IPS는 두 방식의 형식을 모두 받는 패턴 하나로 같은 지표에 모은다. 두 방식 모두 룰에 걸린 트래픽을 떨어뜨리는 inline 방식이므로 화면과 지표, 경보, 저장 쿼리의 이름을 IPS로 통일했다. 설계 문서의 「네트워크 계층」은 아키텍처상 위치를 가리키는 용어라 그대로 둔다.
- **경보는 두 차단 지표에 하나씩 두고, 동작은 연결하지 않는다.** 1분에 10건 이상이면 경보 상태가 된다.
- **대시보드는 위에서 아래로 숫자, 추이, 분포, 상세 순서로 배치한다.** 계층별 합계 숫자와 추이 선, 차단 계층별 분당 추이(계층마다 한 그래프), 경보 상태, 범주별과 룰별 탐지 수와 거부된 포트(막대), 상세 표.
- 같은 대상은 모든 위젯에서 같은 색을 쓴다. 웹 방화벽은 파랑, IPS는 주황, 흐름 거부는 청록이다.

## 근거

- **지표는 형식 차이를 한 번만 푼다.** 필터 패턴에서 두 형식을 받으면, 이후 위젯과 경보는 방식을 몰라도 된다.
- **로그에서 지표로, 지표에서 경보로 가는 것이 운영의 일반적인 경로다.** 경보는 자동 차단(`FR-07`, 선택)의 전 단계다. 동작을 연결하지 않은 것은 `FR-07`을 선택 요구사항으로 남겨 둔 결정(9-C 6번)을 따르기 때문이다.
- **추이 그래프는 한 축만 쓴다.** 두 차단 계층은 단위와 규모가 같다. 흐름 거부는 인터넷 스캐너가 양을 정해 규모가 다르므로 같은 축에 넣으면 두 선이 눌린다. 숫자와 막대로만 보인다.
- **색은 대상을 따른다.** 필터나 방식이 바뀌어도 웹 방화벽은 늘 파랑이다. 색은 참고 팔레트의 1~3번 칸으로, 팔레트 문서에 색각 이상 기준 통과가 기록된 값이다.
- 사용자 정의 지표는 지표당 월 $0.30이고 시간 단위로 계산된다. 이 환경은 필요할 때만 올리므로 비용은 사실상 없다(`NFR-04`).

## 고려한 대안

**Logs Insights 그래프만 사용** — 추가 리소스가 없다. 경보를 걸 수 없고, 쿼리마다 형식 차이를 다시 처리해야 한다.

**경보에 알림 연결** — 알림 주제와 구독을 만들어 이메일을 보낸다. 범위가 늘고, 랩을 올릴 때마다 구독 확인이 필요하다.

**흐름 거부도 추이 그래프에 포함** — 전체를 한 그림에서 본다. 규모가 달라 두 차단 계층의 변화가 보이지 않는다. 두 번째 축은 쓰지 않는다.

## 결과

- 측정 도구는 약 1분 안에 요청을 모두 보낸다. 지표는 1분 해상도라 추이 그래프는 한두 점이 솟는 모양이 된다. 운영 환경처럼 계속 흐르는 트래픽의 모습은 아니다.
- 로그 위젯의 막대 색은 CloudWatch가 정하므로 색 규칙은 지표 위젯에만 적용된다.
- 팔레트 검증 스크립트는 이 환경에 Node.js가 없어 실행하지 못했다. 팔레트 문서에 기록된 검증 결과를 따랐다.
- 필터 패턴이 없는 필드를 참조하는 형식(`||`로 두 경로를 잇는)이 두 방식에서 모두 동작하는지는 배포로 확인한다. Logs Insights에서는 같은 형태의 조건이 한쪽 방식에서 건수를 줄였다(`ADR-030`).

### 배포 후 확인과 수정 (2026-09-25)

- 지표 필터 3개와 경보 2개가 동작했다. 두 형식을 `||`로 받는 IPS 필터 패턴은 Suricata 형식에서도 건수를 맞게 셌다(Logs Insights의 같은 형태 조건과 달리). 측정 1분 동안 두 경보가 `OK`에서 `ALARM`으로 바뀌었다.
- **대시보드를 콘솔에서 보고 세 곳을 고쳤다.**
  - 두 차단 계층을 한 축에 그리자 웹 방화벽(348)의 18분의 1인 IPS(19)가 바닥에 붙었다. 흐름 거부를 뺀 이유가 두 차단 계층 사이에도 성립했다. 계층마다 그래프를 나누고, 맨 위 숫자에 추이 선을 붙였다.
  - 거부 포트를 숫자로 그루핑해 막대의 가로축이 0부터 9090까지의 수 눈금이 됐다. 문자열(`port 123`)로 바꿔 범주 막대로 만들었다.
  - 룰 이름이 막대 축에서 공통 접두어까지만 보였다. 표로 바꿨다.
- **흐름 로그의 NTP 소음을 없앴다.** 거부 포트 막대의 1위가 인스턴스 자신의 123번(NTP)이었다. 운영체제 기본 설정에 들어 있는 공용 NTP 서버로의 시도가 보안 그룹에 막힌 것이다. 세 인스턴스가 링크 로컬 시간 서비스만 쓰도록 공통 스크립트(`scripts/use-amazon-time-sync.sh`)를 두었다. Amazon Linux는 공용 서버 목록을 부팅 때 `/run/chrony.d`에 연결하므로 `/etc`만 고쳐서는 남았고, `/run`을 읽는 설정도 끄도록 고쳤다. 적용 후 123번 거부는 5분당 20~98건에서 0건이 됐고, 거부 포트 상위는 23, 22, 8200, 5222처럼 인터넷 스캐너가 노리는 포트로 바뀌었다.
- 동기화가 끊기면 로그의 시간 순서가 조용히 틀어지므로(`T-08`), 링크 로컬 서버가 선택되지 않으면 초기 구성을 중단한다.
