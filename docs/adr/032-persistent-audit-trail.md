# ADR-032. API 감사 로그는 별도 상시 환경에 두고, 규정 준수 모드 잠금 버킷에 1일 보존한다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 일자 | 2026-09-25 |
| 관련 | `SR-17`, `SR-23`, `NFR-04`, `NFR-06`, `T-07`, `T-15`, `T-18`, `T-24`, `ADR-007`, `ADR-014`, `ADR-030` |

---

## 맥락

`SR-23`은 AWS API 호출을 감사 로그로 남기고 그 무결성을 검증할 수 있어야 한다고 요구한다. `SR-17`은 보안 로그를 계정 권한을 가진 주체도 보존 기간 안에는 삭제할 수 없어야 한다고 요구한다. 계정에는 트레일이 없었고, 기본 이벤트 기록은 90일 조회만 되며 무결성을 검증할 수 없다.

랩(`envs/lab`)은 검증할 때만 만들고 끝나면 지운다. 상태 버킷을 만드는 `bootstrap`은 로컬 상태를 쓰며, 상태를 잃어도 복구할 수 있도록 최소로 유지하기로 했다(`ADR-014`).

## 결정

- **감사 로그를 별도 상시 환경 `envs/audit`에 둔다.** 상태는 기존 상태 버킷에 별도 키로 저장한다.
- **트레일은 모든 리전의 관리 이벤트와 전역 서비스 이벤트를 기록하고, 로그 파일 무결성 검증을 켠다.**
- **저장 버킷은 Object Lock을 켜고, 기본 보존을 규정 준수 모드 1일로 둔다.** 보존이 끝난 객체는 수명 주기 규칙으로 정리한다.
- 버킷 정책은 CloudTrail이 이 트레일 이름으로만 쓰게 제한하고, TLS가 아닌 접근을 거부한다.
- 버킷과 트레일에 삭제 방지(`prevent_destroy`)를 둔다.

## 근거

- **감사 로그는 감사 대상보다 먼저 있어야 한다.** 랩과 함께 만들면 랩을 만드는 호출의 앞부분과 지우는 호출의 뒷부분이 기록에서 빠진다.
- **랩과 수명이 다르다.** 규정 준수 모드 잠금은 루트도 풀 수 없어, 랩과 함께 지우는 구조에 넣으면 삭제가 실패한다.
- **`bootstrap`에 넣지 않는다.** 로컬 상태에 영구 리소스를 늘리면, 상태를 잃었을 때 복구할 범위가 커진다. 별도 환경은 원격 상태의 암호화, 버전 관리, 잠금을 그대로 쓴다. 백엔드 키를 코드에 고정해, 다른 환경의 백엔드 설정 파일을 잘못 써도 랩의 상태 위에 초기화되지 않는다.
- **규정 준수 모드만 요구사항을 충족한다.** 거버넌스 모드는 특별 권한이 있으면 지울 수 있어 「계정 권한을 가진 주체도 삭제할 수 없어야 한다」에 미치지 못한다.
- **보존 1일은 검증에 충분하고 비용이 없다.** 삭제가 거부되는 것을 확인하는 데 하루면 충분하고, 저장량은 하루치 로그뿐이다.
- 계정의 유일한 트레일이라 관리 이벤트 기록은 무료다(`NFR-04`).
- 암호화는 S3 관리형 키(AES256)로 한다. 고객 관리형 키는 키 정책과 월 요금이 추가되고, 이 환경의 위협 모델에서 추가로 막는 경로가 작다.

## 고려한 대안

**`bootstrap`에 추가** — 파일이 늘지 않는다. 로컬 상태의 복구 범위가 커진다(`ADR-014`).

**랩과 함께 생성과 삭제** — 비용이 가장 적다. 랩 생성과 삭제 과정이 기록에서 빠지고, 잠긴 버킷 때문에 삭제가 실패한다.

**거버넌스 모드 잠금** — 운영자가 필요하면 지울 수 있어 관리가 쉽다. `SR-17`을 충족하지 못한다.

**별도 계정으로 로그 격리** — 프로덕션 표준이다. 단일 계정 제약(`C-01`)으로 채택할 수 없다.

## 결과

- **보안 로그(CloudWatch)의 삭제 방지는 이 결정의 범위 밖이다.** CloudWatch Logs에는 잠금 기능이 없다. 내보내기 작업은 잠금 버킷을 지원하지만, 로그가 내보내기 가능해지기까지 최대 12시간이 걸리고 랩은 측정 직후 로그 그룹과 함께 지워진다. 지속 보관에는 구독(전송 스트림)이 권장되며, 이는 로그 그룹마다 전송 경로를 두는 일이라 이번에 만들지 않았다. `SR-17`은 감사 로그에 대해서만 충족한다.
- 버킷은 사실상 계속 남는다. 트레일이 계속 기록하고 새 객체마다 1일씩 잠기므로, 지우려면 트레일을 먼저 멈추고 마지막 객체의 잠금이 끝나기를 기다려야 한다.
- 단일 계정이라 계정 관리자가 트레일 자체를 멈출 수는 있다. 멈춘 기록은 남고, 이미 쓴 로그는 지울 수 없다.

### 배포 후 확인 (2026-09-25)

- 버킷 잠금 설정: 규정 준수 모드 1일. 트레일: 기록 중, 전 리전, 무결성 검증, 전역 이벤트.
- 첫 로그 파일에 대해 관리자 역할로 다음을 시도했고 모두 거부됐다(`Access Denied because object protected by object lock`).
  - 특정 버전 삭제
  - 거버넌스 우회 헤더를 붙인 삭제
  - 보존 기한을 앞당기는 변경
- 버전을 지정하지 않은 삭제는 삭제 표시만 추가됐고, 원본 버전은 남았다.

### 무결성 검증 (2026-09-25)

- 트레일을 만든 뒤 다이제스트 두 개(1시간 단위, 서명과 이전 다이제스트로 연결)가 생긴 시점에 `aws cloudtrail validate-logs`를 실행했다.
- **다이제스트 2개는 유효했고, 로그 파일 14개 중 1개가 `INVALID: not found`였다.** 잠금 시험에서 버전을 지정하지 않고 삭제를 보낸 파일이다. 원본 버전은 잠금으로 남았지만 삭제 표시가 파일을 가렸고, 검증이 다이제스트에 기록된 파일의 누락으로 잡아냈다.
- 삭제 표시를 지우자(삭제 표시 제거는 잠금과 무관하게 허용된다) **다이제스트 2/2, 로그 파일 14/14가 유효**로 돌아왔다.
- 두 통제가 하는 일이 다르다는 것이 한 번에 드러났다. **잠금은 원본이 지워지지 않게 막고, 무결성 검증은 기록이 가려지거나 바뀐 것을 드러낸다.** 잠금이 끝난 뒤에도 검증은 계속 쓸 수 있다(`SR-23`).
