# ADR-027. 직접 운영 검사 계층은 단일 인스턴스에서 netfilter 큐로 inline 구성한다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 일자 | 2026-09-25 |
| 관련 | `FR-02`, `FR-10`, `SR-03`, `SR-06`, `SR-07`, `SR-13`, `SR-14`, `T-30`, `F13`, `ADR-004`, `ADR-006`, `ADR-012`, `ADR-019`, `ADR-021`, `ADR-022` |

---

## 맥락

`ADR-004`에서 직접 운영 방식을 Ubuntu와 Suricata로 정했고, `ADR-012`에서 검사 프로세스가 멈추면 트래픽을 차단하기로 했다. 이 문서는 그 결정을 인스턴스 위에서 구현하는 방식을 정한다.

인스턴스가 남의 트래픽을 검사하고 전달하려면 AWS가 인터페이스에서 패킷을 버리지 않아야 하고, 운영체제가 패킷을 전달해야 하며, 전달하기 전에 검사 프로세스가 판정해야 한다. 원본 환경은 이 중 전달 설정이 문서에 없었다(`F13`).

## 결정

- **전달 경로만 netfilter 큐로 보낸다.** nftables의 forward 훅에 `queue num 0`을 두고 우회(bypass) 옵션은 두지 않는다. Suricata는 큐 모드(`-q 0`)로 실행한다.
- **패키지의 기본 서비스를 쓰지 않고 inline 전용 서비스를 따로 둔다.** 기본 서비스는 사본만 보는 패시브 모드로 실행된다.
- **룰은 공유 파일 하나만 불러온다**(`-S`). 패키지가 가리키는 기본 룰셋은 섞지 않는다. 내부 대역은 실행 인자로 준다.
- **기동을 검증하고 실패하면 초기 구성을 중단한다.** 커널에 큐 0을 받는 프로세스가 등록됐는지, 파일의 룰이 모두 불러와졌는지 확인한다.
- **인스턴스에 자동 할당 공인 IP를 붙인다.** 탄력적 IP는 쓰지 않는다.
- **보안 그룹의 80과 443 인바운드는 웹 방화벽이 받는 출발지로 한정한다.** 웹 방화벽 자신이 나가는 443은 웹 방화벽 서브넷에서 오는 트래픽으로 따로 허용한다.
- 인스턴스 크기는 `t3.small`, 이벤트 로그는 디스크에 두고 전송은 Phase 10에서 정한다.

## 근거

- **전달 경로만 큐에 넣어야 고칠 수단이 남는다.** fail-close에서 검사 프로세스가 멈추면 큐에 들어간 패킷은 모두 버려진다. 인스턴스 자신의 통신까지 큐에 넣으면 세션 관리자 접속도 끊겨 들어갈 방법이 사라진다. forward 훅만 쓰면 인스턴스 자신의 통신은 검사와 무관하게 유지된다.
- **우회 옵션을 빼는 것이 곧 fail-close다.** 큐를 받는 프로세스가 없을 때 커널이 패킷을 통과시킬지는 이 옵션 하나로 결정된다(`ADR-012`).
- **조용한 실패를 기동 단계에서 잡아야 한다.** 큐 모드로 바꾸는 데 실패하면 Suricata는 패시브로 정상 기동하고, 큐에는 받을 프로세스가 없어 전달 트래픽이 모두 버려진다. 룰 하나가 문법 오류면 경고만 남기고 나머지로 실행된다. 두 경우 모두 서비스 상태는 정상으로 보인다.
- **기본 룰셋을 섞으면 비교가 깨진다.** 두 방식의 차이가 운영 모델에서만 나오려면 같은 룰만 적용돼야 한다(`ADR-022`).
- **NAT를 거쳐 나갈 수 없다.** NAT의 기본 경로가 이 인스턴스로 향하므로 인스턴스 자신의 통신이 자기에게 되돌아온다. 이 인스턴스가 있는 서브넷의 기본 경로는 전달한 트래픽이 나가는 길이라 NAT로 바꿀 수도 없다. 경계 계층의 인터넷 노출은 `SR-03`이 허용한다. 이 주소로 접속하는 주체가 없으므로 고정 주소가 필요 없다.
- **보안 그룹은 전달 트래픽과 인스턴스 자신에게 온 트래픽을 구분하지 못한다.** 80과 443을 전체에 열면 인스턴스 자신의 공인 주소도 열린다. 웹 방화벽이 이미 운영자 주소만 받으므로(`ADR-019`), 같은 범위로 좁혀도 잃는 트래픽이 없다.
- 룰과 흐름 테이블은 기동 시 메모리에 올라간다. 1GiB에서는 운영체제와 에이전트를 빼면 여유가 작다.

## 고려한 대안

**패키지 기본 서비스를 덮어쓰기(drop-in)로 수정** — 파일이 하나 줄어든다. 기본 서비스가 실행 인자를 어디서 읽는지가 패키지 버전에 따라 달라질 수 있어, 덮어쓰기가 조용히 무시될 위험이 있다.

**인스턴스 자신의 통신까지 큐에 넣기** — 검사 범위가 넓어진다. 검사 프로세스가 멈추면 관리 접근까지 끊긴다.

**네트워크 인터페이스 2개로 관리와 전달을 분리** — 관리 통신을 NAT로 보낼 수 있어 공인 주소가 필요 없다. 정책 라우팅을 직접 구성해야 하고, 아키텍처 문서에서 단일 인터페이스로 단순화한 결정을 되돌린다.

**VPC 엔드포인트로 세션 관리자 연결** — 공인 주소 없이 관리 접속이 된다. 엔드포인트 3개의 시간당 요금이 공인 주소의 약 8배이고, 패키지 저장소에는 여전히 인터넷 경로가 필요하다(`ADR-015`).

**탄력적 IP** — 주소가 고정된다. 이 주소를 참조하는 곳이 없으므로 고정할 이유가 없고, 리소스가 하나 늘어난다.

## 결과

- **공인 IPv4 주소가 3개가 된다**(웹 방화벽, NAT, Suricata). 추가 비용은 시간당 $0.005다.
- **인스턴스 한 대가 단일 장애점이다.** 검사 프로세스가 멈추면 웹 서비스와 앱의 아웃바운드가 끊긴다. 관리형 방식은 이 결정을 사용자에게 맡기지 않는다(`ADR-012`).
- **아웃바운드는 좁힐 수 없다.** 전달할 목적지를 미리 알 수 없기 때문이며, 이 인스턴스가 장악되면 측면 이동의 발판이 된다(`T-30`).
- 룰 파일이 사용자 데이터에 포함된다. 현재 약 12KB로 한도 16KB 안이지만, 룰이 늘면 한도에 닿는다. 그때는 파일을 객체 저장소나 시크릿 저장소로 옮긴다.
- 이벤트 로그가 인스턴스 디스크에만 있어 `SR-14`(인스턴스에 종속되지 않는 수집 경로)는 Phase 10에서 충족된다. 웹 방화벽과 앱도 아직 수집 에이전트가 없으므로 세 인스턴스를 함께 처리한다.
- 관리형 방화벽이 쓰는 Suricata 버전은 공개돼 있지 않다. 두 방식의 룰별 결과가 다르면 엔진 버전과 기본 설정의 차이를 원인 후보로 기록한다.
