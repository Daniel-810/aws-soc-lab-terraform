# ADR-020. 계층별 탐지 측정은 직접 만든 도구로 수행한다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 |
| 일자 | 2026-09-20 |
| 관련 | `AC-05a`, `AC-05b`, `SR-11`, `SR-12`, `FR-10`, `T-11`, `ADR-018`, `F1` |

---

## 맥락

Phase 1에서 탐지율 정량화 도구로 GoTestWAF를 채택했다. Phase 7의 4단계에 착수하며 실제로 적용해 보니 이 랩의 측정 요구를 충족하지 못한다.

GoTestWAF는 응답 코드로 차단 여부를 판정한다. 차단률을 재는 도구이며 그 목적에는 정확하다. 그러나 이 프로젝트가 측정해야 하는 것은 네 가지다.

| 측정 | 필요 시점 | 응답 코드로 가능한가 |
|---|---|---|
| 웹 방화벽 차단률 | Phase 7 4단계, 6단계 | 가능 |
| **탐지 전용 상태의 탐지율** | Phase 7 5단계 | 불가. 아무것도 차단하지 않으므로 룰셋 유무와 무관하게 0이 된다 |
| **동일 요청의 계층별 탐지 비교** | Phase 8, 9, 11 | 불가. 네트워크 방화벽과 침입 방지 시스템은 응답을 바꾸지 않고 기록만 남기는 경우가 있다 |
| **아웃바운드 검사** | Phase 8, 9 | 불가. 인바운드 요청만 다룬다 |

`ADR-018`은 탐지 전용으로 먼저 적용하고 측정한 뒤 차단으로 전환하도록 정했는데, 그 2단계를 측정할 수단이 없다는 뜻이다. 또한 `T-11`에서 평문 경로를 의도적으로 유지한 이유가 계층별 탐지 범위 실증인데, 요청 단위로 계층을 비교할 방법이 없으면 그 근거도 만들 수 없다.

부수적으로, 이 도구는 컨테이너 실행 환경이나 Go 빌드 환경을 요구한다. 작업 장비에는 둘 다 없고, `ADR-019`에 따라 경계 계층은 작업 장비의 주소만 허용하므로 다른 장비에서 실행할 수도 없다.

## 결정

**측정 도구를 직접 작성한다(`tools/probe/`).** 요청마다 고유 식별자를 부여해 헤더와 질의 문자열에 함께 싣고, 각 계층의 로그에서 그 식별자를 찾아 요청 단위로 집계한다.

**공격 페이로드는 GoTestWAF의 테스트 케이스를 수정 없이 사용한다.** 도구는 쓰지 않고 페이로드만 가져오며, 출처와 사용 조건(MIT)을 저장소에 함께 둔다.

판정 기준은 두 가지로 분리한다.

- **탐지** — 해당 식별자에 대해 **룰이 일치한 기록**이 로그에 존재한다. 로그에 존재하기만 하는 것으로는 부족하다. 권장 설정은 응답 상태만으로도 기록을 남기므로, 애플리케이션 오류가 탐지로 집계될 수 있다.
- **차단** — 응답이 차단 상태 코드로 돌아왔다.

## 근거

- **탐지 전용 상태를 측정할 수 있는 유일한 방법이 로그 대조다.** 응답이 동일하므로 외부에서 관찰 가능한 차이가 없다. `ADR-018`의 2단계는 이 방법이 없으면 성립하지 않는다.
- **식별자를 심는 방식은 계층이 늘어나도 그대로 확장된다.** Phase 8과 9에서 대상 로그만 추가하면 같은 요청에 대해 어느 계층이 무엇을 보았는지가 표로 정리된다. 방식 A와 방식 B의 비교도 같은 자료로 수행한다.
- **페이로드를 공개 모음에서 가져오므로 비교 가능성이 유지된다.** 직접 작성한 페이로드로 측정하면 수치의 의미를 설명하기 어렵다.
- **추가 도구를 설치하지 않는다.** 표준 라이브러리와 YAML 구문 분석기 하나만 사용한다. 공급망에 추가되는 항목이 최소화된다.
- 식별자를 헤더와 질의 문자열 양쪽에 싣는 이유는 계층마다 기록하는 범위가 다르기 때문이다. 요청 줄만 기록하는 계층에서도 대조가 가능해야 한다.

## 고려한 대안

**GoTestWAF 유지** — 차단률 측정은 이 도구가 낫고 널리 쓰인다. 위 표의 세 항목을 측정할 수 없어 채택하지 않는다. 페이로드를 그대로 사용하므로 결과는 비교 가능한 범위에 있다.

**두 도구 병행** — 차단률은 GoTestWAF, 나머지는 자체 도구. 같은 대상을 두 도구로 재면 수치가 어긋날 때 원인을 가리기 어렵고, 실행 환경 문제도 그대로 남는다.

**패킷 재생 도구로 침입 방지 시스템만 따로 측정** — Phase 9에는 적합하나 웹 방화벽과 동일한 요청으로 비교할 수 없어 계층 비교라는 목적을 달성하지 못한다.

## 결과

- **도구를 유지보수해야 한다.** 계층이 추가될 때마다 로그 형식을 해석하는 코드가 필요하다. 각 계층의 로그 구조를 이해해야 한다는 점은 이 프로젝트의 학습 목표와 어긋나지 않는다.
- **"업계 표준 도구로 측정했다"고 말할 수 없다.** 대신 페이로드 출처와 판정 기준을 문서로 공개해 재현 가능성을 확보한다.
- **측정 결과는 저장소에 포함하지 않는다.** 공인 주소와 요청 전문이 포함되므로 `SR-10`의 대상이다. 요약 수치만 문서에 옮긴다.
- **현재 페이로드는 한 위치(질의 문자열)에만 삽입된다.** 경로나 본문에 넣어야 의미가 있는 페이로드가 있어 탐지율이 실제보다 낮게 측정된다. 5단계 측정 전에 삽입 위치를 확장한다. 4단계 기준선은 룰셋이 없어 영향을 받지 않는다.
- 식별자가 요청에 포함되므로 **측정용 요청임이 로그에 드러난다.** 실제 공격과 구분되는 것은 이 환경에서는 이점이다.
