## 1. 배경 및 목적

### 1.1 배경

2025년 8월, VMware ESXi 기반 온프레미스 보안관제 실습 환경을 AWS로 이전하는 프로젝트를 2인 팀으로 수행했다. 방화벽 계층을 오픈소스와 관리형 두 방식으로 각각 구축해 비교하고, 이기종 로그를 CloudWatch로 단일화하며, 관제 대시보드까지 구성했다.

구축은 전 과정이 **콘솔 수동 작업**이었고, 산출물은 클릭 순서를 기록한 매뉴얼이다. 이 방식에서 아래 세 가지 한계가 확인됐다.

| # | 한계 | 근거 |
|---|---|---|
| 1 | **재현 불가능** | 인스턴스 IP·ENI 이름이 설정 파일에 하드코딩되어 있어, 리소스를 재생성하면 프록시 설정과 로그 수집이 조용히 끊긴다 |
| 2 | **방어가 검증되지 않음** | WAF에 OWASP CRS가 설치되지 않아 탐지 룰이 0개였다. 감사 로그만 쌓였을 뿐 실제 차단은 일어나지 않았다 |
| 3 | **로그 파이프라인 취약** | 방화벽 어플라이언스가 FreeBSD 기반이라 공식 로그 에이전트를 쓸 수 없었고, 우회 수단이 인스턴스 식별자에 종속됐다 |

원본 환경에서 발견된 결함 전체는 **부록 A**에 `F1`~`F16`으로 정리했다.

### 1.2 목적

동일한 아키텍처를 **코드로 재구성**하여 위 세 한계를 해소하고, 두 방화벽 방식의 비교를 정성적 인상에서 **측정 가능한 근거**로 끌어올린다.

부수 목표로, 구축 과정에서 AWS 보안 서비스와 클라우드 보안 설계 원칙을 실제 의사결정을 통해 습득한다.

## 2. 범위

### 2.1 In scope

- VPC 네트워크 기반 구조 (서브넷, 라우팅, 보안그룹, 게이트웨이)
- 보호 대상 웹 애플리케이션 (단일 인스턴스)
- L7 웹 방화벽 계층 (룰셋 포함)
- L3/L4 네트워크 방화벽 계층 — **관리형과 직접 운영 두 방식**
- 로그 중앙 수집 및 시각화
- 공격 재현 및 탐지 검증 수단
- 전 구성 요소의 코드화 및 자동 검증

### 2.2 Out of scope

범위에서 제외한 항목과 그 근거를 명시한다. 근거 없는 제외는 방어할 수 없다.

| 제외 항목 | 근거 |
|---|---|
| 멀티 계정 / AWS Organizations | 단일 계정 제약(3.2). 계정 분리는 조직 거버넌스 주제로, 본 프로젝트의 네트워크·워크로드 보안 초점과 다르다 |
| 컨테이너 / Kubernetes | 원본 환경이 EC2 기반이며, 재구성의 목적은 동일 아키텍처의 IaC 전환이다. 오케스트레이션 도입은 아키텍처 변경이지 재구성이 아니다 |
| 멀티 리전 / DR | 가용성 목표(NFR-05)가 이를 요구하지 않는다 |
| 실사용자 트래픽 / 프로덕션 운영 | 검증용 랩 환경이다. 성능·용량 요구사항을 정의하지 않는다 |
| WAF 우회 기법 연구 | 방어 구성 검증이 목적이며, 우회 연구는 별도 주제다 |
| 자동 차단 대응(SOAR) | **선택 요구사항(FR-07)으로 분류.** 시간이 허용되면 수행한다 |

### 2.3 사용자

| 구분 | 설명 |
|---|---|
| 구축·운영자 | 1인. 설계·구현·검증을 모두 수행한다 |
| 검증 수행자 | 구축자와 동일. 공격 페이로드를 주입하고 탐지 결과를 확인한다 |

## 3. 가정 및 제약

### 3.1 가정

- 원본 환경의 아키텍처 의도(2계층 방어, 중앙 로깅, 관제 대시보드)는 유효하며 유지한다.
- 두 방화벽 방식은 **동일한 탐지 엔진**을 사용할 수 있다. 따라서 엔진 차이가 아닌 운영 모델 차이만 비교 대상이 된다.

### 3.2 제약

| ID | 제약 | 영향 |
|---|---|---|
| `C-01` | 단일 AWS 계정 | 계정 분리 기반 격리 설계 불가 |
| `C-02` | 리전 `ap-northeast-2` 고정 | 원본 환경과 동일 |
| `C-03` | **운영 인력 1인** | 운영 부담이 큰 선택지는 실질적으로 채택 불가. 설계 결정의 핵심 근거 |
| `C-04` | 개인 비용 부담 — **월 30,000원 상한** | 상시 운영 불가. 기동 시간을 예산에서 역산해 관리한다 |
| `C-05` | 구축 기간 약 2주 | 범위 확대 시 완성도 저하 |

## 4. 기능 요구사항 (FR)

> 제품·서비스명을 명시하지 않는다. 무엇을 하는지만 정의하고, 어떻게 할지는 설계(`03-architecture.md`)에서 결정한다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| `FR-01` | 인터넷에서 접근 가능한 웹 애플리케이션을 제공하며, 이를 보호 대상으로 한다 | 필수 |
| `FR-02` | 인바운드 트래픽에서 **알려진 네트워크 공격 시그니처를 탐지하고 차단**할 수 있어야 한다 | 필수 |
| `FR-03` | HTTP 요청에서 **알려진 웹 애플리케이션 공격 패턴을 탐지하고 차단**할 수 있어야 한다 | 필수 |
| `FR-04` | `FR-02`의 탐지 기능을 **관리형 방식과 직접 운영 방식 두 가지로 각각 구성**할 수 있어야 하며, 두 방식은 전환 가능해야 한다 | 필수 |
| `FR-05` | 각 보안 계층에서 발생한 이벤트 로그를 **단일 지점으로 수집**해야 한다 | 필수 |
| `FR-06` | 수집된 로그에서 공격자 IP, 탐지 시그니처, 요청 페이로드를 **조회하고 시각화**할 수 있어야 한다 | 필수 |
| `FR-07` | 탐지된 공격 출발지를 **자동으로 차단**할 수 있어야 한다 | 선택 |
| `FR-08` | 정의된 공격 페이로드를 주입하여 **탐지 여부를 재현 가능하게 검증**할 수 있어야 한다 | 필수 |
| `FR-09` | 환경 전체를 **생성하고 완전히 삭제**할 수 있어야 한다 | 필수 |

**`FR-07` 해설** — 필수 범위 완료 후 잔여 시간이 있을 때 수행한다. 미구현 시 `F9`(수동 차단)는 미해결로 남으며, 그 사실을 최종 문서에 명시한다.

**`FR-04` 해설** — 이 요구사항이 프로젝트의 핵심이다. 두 방식이 같은 요구사항을 만족하되 운영 특성이 다르다는 점을 비교하기 위한 것이며, 제품 선택을 요구사항 단계에서 하지 않는 이유이기도 하다.

## 5. 비기능 요구사항 (NFR)

| ID | 요구사항 | 측정 방법 | 우선순위 |
|---|---|---|---|
| `NFR-01` | 환경 전체가 **코드로 정의**되어야 한다. 콘솔 수동 조작이 필요한 구성 요소가 없어야 한다 | 신규 계정에서 코드만으로 구축 성공 | 필수 |
| `NFR-02` | 전체 삭제 후 재생성이 **⚠️ 30분 이내** 완료되어야 한다 | `destroy` → `apply` 소요 시간 측정 | 필수 |
| `NFR-03` | 재생성 후 별도 수동 조치 없이 **검증(`FR-08`)이 전부 통과**해야 한다 | 검증 스크립트 종료 코드 | 필수 |
| `NFR-04` | **월 총비용이 30,000원을 초과하지 않아야** 한다. 전체 기동 단가는 시간당 1,000원 이하, 비기동 상태 유지비는 월 5,000원 이하로 한다 | 예산 알람 및 실제 청구액 | 필수 |
| `NFR-05` | 가용성 이중화는 **요구하지 않는다.** 다만 코드는 가용영역 수를 변수로 받아 확장 가능해야 한다 | 변수 변경만으로 다중 AZ 배포 가능 | 필수 |
| `NFR-06` | 로그 보존 기간은 **14일**로 하며, 무기한 보존하지 않는다 | 로그 그룹 설정 확인 | 필수 |
| `NFR-07` | 인스턴스 초기 구성이 **5분 이내** 완료되어야 한다. 이를 위해 보안 소프트웨어는 **배포판 패키지로 설치**하며 소스 컴파일하지 않는다 | 부팅부터 서비스 정상화까지 측정 | 필수 |
| `NFR-08` | 코드 변경 시 **자동 검사**(형식·유효성·보안)를 통과해야 병합 가능하다 | CI 파이프라인 통과 여부 | 권장 |
| `NFR-09` | 각 구성 모듈은 **독립적으로 이해 가능**해야 하며, 입력과 출력이 문서화되어야 한다 | 모듈 문서 존재 여부 | 권장 |

**`NFR-07` 해설** — 원본은 최소 사양 인스턴스에서 소스를 컴파일해 30분 이상 소요됐다(`F11`). 배포판 패키지를 사용하면 컴파일이 사라져 `NFR-02`(재생성 시간)와 충돌하지 않는다. **패키지 가용 여부는 Phase 7 착수 시 최우선 확인 사항이며, 불가할 경우 사전 이미지 방식으로 전환한다.**

**`NFR-05` 해설** — 단일 AZ를 선택한 근거는 `C-04`(비용)이며, 랩 환경이므로 장애 시 재생성이 허용된다(`NFR-02`). 다만 이를 "HA를 몰라서 안 한 것"과 구분하기 위해 코드 차원의 확장성을 요구사항으로 남긴다.

## 6. 보안 요구사항 (SR)

> 도출 출처: ① 원본 환경 결함(부록 A) ② AWS Well-Architected 보안 기둥 ③ 위협 모델링(`02-threat-model.md`)
>
> `SR-17`~`SR-22`는 Phase 2 위협 모델링에서 신규 도출되었다. 「출처 위협」 열이 근거다.

### 6.1 접근 통제

| ID | 요구사항 | 대응 결함 | 우선순위 |
|---|---|---|---|
| `SR-01` | 모든 인스턴스에 **SSH 인바운드 규칙이 존재하지 않아야** 하며, 관리 접근은 세션 관리 서비스로만 가능해야 한다 | `F5` | 필수 |
| `SR-02` | 인스턴스 메타데이터 서비스는 **세션 토큰 방식만 허용**해야 하며, **응답 홉 제한을 최소값으로 설정**해야 한다 | `F6` | 필수 |
| `SR-03` | 인터넷에서 직접 도달 가능한 자산은 **경계 계층으로 한정**한다. 그 외 모든 인스턴스는 프라이빗 서브넷에 위치한다 | `F2` | 필수 |
| `SR-04` | 보안그룹은 **출발지를 다른 보안그룹으로 참조**하여 정의한다. CIDR 전체 개방(`0.0.0.0/0`)은 경계 계층의 서비스 포트에만 허용한다 | `F2` | 필수 |
| `SR-05` | 관리 콘솔 및 API 접근에는 **만료되는 자격 증명**을 사용한다. 장기 액세스 키를 생성하지 않는다 | — | 필수 |
| `SR-18` | 경계 계층에서 수신한 **프록시 관련 헤더를 신뢰하지 않아야** 하며, 출처 판단은 실제 연결 정보를 기준으로 한다 | — | 필수 |

### 6.2 권한

| ID | 요구사항 | 대응 결함 | 우선순위 |
|---|---|---|---|
| `SR-06` | 각 인스턴스 역할은 **필요한 작업과 대상 리소스로 범위를 한정**해야 한다. 관리형 정책을 그대로 부여하지 않는다 | — | 필수 |
| `SR-07` | 하나의 역할을 여러 용도로 공유하지 않는다 | — | 권장 |

### 6.3 데이터 보호

| ID | 요구사항 | 대응 결함 | 우선순위 |
|---|---|---|---|
| `SR-08` | 보호 대상과 웹 방화벽 계층 사이의 통신은 **암호화**되어야 하며, **인증서 검증을 비활성화하지 않는다** | `F3` | 필수 |

| `SR-20` | 응답은 **시스템 구성과 탐지 로직에 관한 정보를 노출하지 않아야** 한다. 차단 응답은 단일 형태로 통일한다 | `F16` | 필수 |
| `SR-24` | 시크릿은 **인스턴스 사용자 데이터·코드·상태 파일에 평문으로 포함되지 않아야** 하며, 실행 시점에 전용 관리 수단에서 조회되어야 한다 | — | 필수 |

### 6.5 로깅 및 추적성

| ID | 요구사항 | 대응 결함 | 우선순위 |
|---|---|---|---|
